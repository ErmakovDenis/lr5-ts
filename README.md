# ЛР5 — структура данных для хранения словаря языка

Лабораторная работа по структурам данных. Код: <https://github.com/ErmakovDenis/lr5-ts>

## 1. Проект

TypeScript, модули ES. Node с 23-й версии запускает `.ts` сам, поэтому сборки нет.
Библиотек нет, тесты запускает встроенный тест-раннер.

```
src/trie.ts             обычное префиксное дерево
src/compressed-trie.ts  сжатое дерево (radix tree)
src/array-trie.ts       дерево на плоском массиве, по 33 ячейки на узел
src/dawg.ts             автомат со склейкой окончаний — основной вариант
src/index.ts            демонстрация
test/                   46 тестов
bench/benchmark.ts      замеры памяти и скорости
data/                   словарь из 138 874 русских слов
```

| Команда | Что делает |
|---|---|
| `npm start` | демонстрация |
| `npm test` | прогон тестов |
| `npm run bench` | замеры на настоящем словаре |
| `npm run typecheck` | проверка типов |

Все четыре структуры реализуют один интерфейс, то есть выполняют все три
функциональных требования:

```ts
export type Dictionary = {
  add(word: string): void;              // добавить одно слово
  addAll(words: Iterable<string>): void; // добавить список слов
  has(word: string): boolean;            // проверить, есть ли слово
  readonly size: number;
};
```

Замеры сделаны на словаре из системного hunspell: **138 874 слова, 1 431 307
символов**, средняя длина слова 10.3. Дальше по тексту `N` — число символов во
всех словах, `W` — число слов, `L` — длина проверяемого слова, `A` — размер
алфавита (для русского 33).

## 2. Почему не Set

`Set<string>` решает задачу в одну строчку, но хранит каждое слово целиком, то
есть занимает O(N) памяти. По условию нужно строго меньше, поэтому нужна
структура, которая не хранит одинаковые куски слов по многу раз.

Побочно теряется и полезная возможность: у `Set` нельзя спросить «есть ли слова,
начинающиеся на „кор“», а у дерева это тот же проход, что и обычный поиск.

## 3. Префиксное дерево

Слово — это путь от корня вниз, одна буква на одно ребро. Общее начало у слов
хранится один раз: «кора» и «корова» делят первые три узла. Узел помечается
флагом `isWord`, иначе нельзя отличить слово «кот» от начала слова «котенок».

| Операция | Сложность | Почему |
|---|---|---|
| `add(word)` | O(L) | спускаемся по буквам слова, попутно создавая узлы |
| `addAll` | O(N) | сумма длин всех слов |
| `has(word)` | O(L) | тот же спуск |
| память | O(число узлов) | узел на каждый различный префикс |

Важно, что время не зависит от количества слов: поиск в словаре из ста слов и из
миллиона стоит одинаково. У `Set` формально тоже O(L) — хеш нужно посчитать по
всему слову, — но на практике он быстрее, об этом в разделе 7.

Узлов в дереве ровно столько, сколько в словаре различных префиксов. На реальном
словаре получилось **521 839 узлов при N = 1 431 307**, то есть 36% от N. То есть
дерево экономит в три раза, но по порядку роста это всё ещё O(N): если слова не
имеют общих начал, узлов будет почти N.

## 4. Ведущий множитель: как хранить потомков

Асимптотика ничего не говорит про то, сколько стоит один узел, а разница
огромная.

**Массив на весь алфавит.** Классический вариант из учебников: в узле массив из
33 ячеек, по ячейке на букву, в ячейке номер потомка. Поиск буквы — это одно
обращение по индексу, без всякого поиска. Но память становится **O(A × число
узлов) = O(33 × число узлов)**, и это тот самый ведущий множитель из задания.
Большинство ячеек пустые: у узла в середине слова потомок обычно один.

В замерах: 521 839 узлов × 33 ячейки = **17 220 687 ячеек**, по 4 байта на номер
потомка — **66 МБ**, при том что полезных из них меньше 3%.

**Map.** Хранит только существующие рёбра, поэтому ячеек ровно столько, сколько
нужно: `число узлов - 1`. Зато один элемент `Map` в V8 стоит сильно дороже
четырёх байт — по замерам вышло **124 МБ**, то есть около 240 байт на узел.

Получается забавное: вариант, который «тратит 33 ячейки на узел», по факту занял
вдвое меньше варианта, который «хранит только нужное». Ведущий множитель и
стоимость одной ячейки важнее, чем число ячеек.

## 5. Сжатое дерево

В обычном дереве много узлов с единственным потомком: в слове «абажурчик» после
«абажур» развилок почти нет, а узел на каждую букву всё равно создаётся. В
сжатом дереве такие цепочки склеены в одно ребро, на котором написан сразу кусок
слова.

Узлов остаётся столько, сколько в дереве листьев и развилок, то есть **не больше
2W**: на реальном словаре **194 051 узел, 1.40 на слово**. По сравнению с
обычным деревом в 2.7 раза меньше объектов и памяти 59 МБ вместо 124 МБ.

Но суммарная длина меток осталась прежней — те же 521 838 символов. То есть
количество *объектов* стало O(W), а количество хранимых *символов* по-прежнему
столько же, сколько узлов в обычном дереве.

## 6. Автомат со склейкой окончаний (DAWG)

Дерево склеивает только одинаковые начала слов. Но в русском полно одинаковых
окончаний: «красный», «умный», «честный» заканчиваются на «ный», и в дереве
каждое из них хранит эти буквы отдельно.

Если заметить, что у таких слов хвосты устроены совершенно одинаково, их можно
хранить один раз — тогда несколько рёбер ведут в один и тот же узел, и из дерева
получается граф.

Строится алгоритмом Дачука: слова подаются по алфавиту, и как только часть дерева
перестаёт меняться, она сразу минимизируется. У каждого готового узла считается
отпечаток — конец слова или нет и куда ведут рёбра, — и если такой узел уже
встречался, новый выбрасывается, а ребро вешается на старый.

```ts
private fingerprint(node: Node): string {
  let key = node.isWord ? '1' : '0';
  for (const [char, child] of node.children) key += `|${char}${child.id}`;
  return key;
}
```

Сравнивать достаточно номера потомков, а не поддеревья целиком, потому что
потомки к этому моменту уже минимизированы.

Результат на настоящем словаре: **59 196 узлов вместо 521 839**, в 8.8 раза
меньше дерева и **4.1% от N**. Памяти 17 МБ против 124 МБ. Поиск при этом
устроен ровно как в дереве — то, что узлы общие, на спуске никак не сказывается,
и время остаётся O(L).

**Чего это стоит.** Минимальный автомат — структура статическая: добавить в него
слово, не перестраивая всё, нельзя. Поэтому слова, пришедшие после построения,
складываются в обычное дерево рядом, а `has` смотрит в оба места. Пока таких слов
немного, это ничего не стоит; если их накопится много, словарь надо перестроить.

**Честная оговорка про «строго меньше O(N)».** Экономия автомата держится на том,
что в языке много одинаковых окончаний. Я проверил его на 138 874 случайных
строках той же длины — там узлов получилось 33% от N, то есть выигрыш у дерева
всего в 2.1 раза вместо 8.8. Так что по порядку роста в худшем случае это
по-прежнему O(N); строго меньше N структура становится именно на осмысленном
словаре, и чем он больше, тем сильнее эффект — новые слова почти целиком
собираются из уже имеющихся кусков.

## 7. Замеры

`npm run bench` на словаре из 138 874 слов. Памяти меряю как прирост кучи плюс
отдельно выделенные массивы — типизированные массивы в куче не учитываются.

| Структура | Память, МБ | На слово, байт | Построение, мс | Узлов |
|---|---|---|---|---|
| `Set` (для сравнения) | 5.1 | 38 | 22 | — |
| Trie | 124.4 | 940 | 151 | 521 839 |
| CompressedTrie | 58.9 | 445 | 109 | 194 051 |
| ArrayTrie (33 буквы) | 66.8 | 504 | 146 | 521 839 |
| Dawg | 16.9 | 128 | 190 | 59 196 |

У `Set` число маленькое, потому что строки уже прочитаны из файла и он кладёт к
себе только ссылки на них. Сами строки весят ещё около 6 МБ, и без них `Set`
работать не может, а деревьям исходные строки после построения не нужны.

Проверка слова, 200 000 запросов, половина существующих слов и половина
испорченных:

| Структура | Время, мс | На запрос, нс |
|---|---|---|
| `Set` | 3.9 | 19 |
| Trie | 347.5 | 1738 |
| CompressedTrie | 310.1 | 1550 |
| ArrayTrie (33 буквы) | 150.7 | 754 |
| Dawg | 168.1 | 841 |

`Set` быстрее всех почти в сорок раз, и это ожидаемо: он считает хеш по всему
слову за один проход и делает одно обращение в таблицу, а дерево делает десять
отдельных поисков по `Map` — по одному на букву. `ArrayTrie` быстрее остальных
деревьев ровно потому, что вместо поиска по `Map` у него обращение по индексу.
`Dawg` обгоняет обычное дерево почти вдвое: узлов в девять раз меньше, они лучше
помещаются в кэш процессора.

## 8. Тесты

46 тестов, запуск `npm test`. Один и тот же набор прогоняется по всем четырём
реализациям — они должны вести себя одинаково. Проверяю пустой словарь, слово из
одной буквы, слово, которое является началом другого («кот» и «котенок»),
середину слова, повторные добавления, слова без общего начала.

Отдельно: каждая структура сверяется с обычным `Set` на 500 случайных словах,
причём проверяются и те слова, что в словаре есть, и те, которых нет. И есть
тесты на сами оптимизации — что сжатое дерево даёт меньше узлов, чем обычное, а
автомат меньше, чем сжатое, на словах с общим окончанием.

## 9. Выводы

| Структура | Память | `add` | `has` | Узлов от N |
|---|---|---|---|---|
| Trie | O(узлов), 33×узлов для массива | O(L) | O(L) | 36% |
| CompressedTrie | O(W) объектов, O(узлов) символов | O(L) | O(L) | 13% |
| Dawg | O(узлов после склейки) | O(L) | O(L) | 4.1% |

Все операции стоят O(L) и не зависят от размера словаря — это главное, что даёт
дерево. Требование «памяти строго меньше O(N)» выполняется за счёт того, что
одинаковые куски слов хранятся один раз: обычное дерево ужимает словарь до 36% от
N, автомат — до 4.1%.

Но по замерам видно, что ведущий множитель решает не меньше асимптотики. Дерево
на `Map` занимает 124 МБ при 36% узлов от N, а `Set`, который по условию «плохой»
и тратит O(N), — 5 МБ. Вся разница в том, что узел с `Map` стоит порядка 240 байт,
а ссылка на строку — 38. Чтобы выигрыш по числу узлов превратился в выигрыш по
памяти, узел должен быть дешёвым: либо массив чисел вместо `Map`, либо, как в
`Dawg`, узлов должно стать на порядок меньше.
